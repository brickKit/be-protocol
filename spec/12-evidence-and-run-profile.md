# 12 运行档案、告警渠道与证据

依据：装配项目协议 15（备份、恢复与一致性恢复）的证据表、证据的写入与第 6 步，底层选择的“不随恢复回退的存储”，A139。整套恢复把业务库带回某一时刻 T，本章的三样东西在 T 之后仍然记得：

- **运行档案**：部署之外、只追加的记录，存部署恢复代次与授权恢复代次的权威计数、信任材料、恢复中的步骤记录；
- **告警渠道**：证据存储不可达时，记录者把签名的完整记录发到这里；
- **证据**：收紧、放宽、对外命令等记录，存在证据存储（审计组件兼任）。

证据的条款从 P12.9 起；SDK 一侧怎样写证据（两段写的意图与结论、时限、告警渠道）随 SDK 的实现补上。

## 运行档案

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P12.1 | 必须 | 运行档案是一个开了对象锁的对象存储桶，锁为合规模式：保留期内任何身份都删不掉、改不短。每条记录一个对象，键为 `<部署>/<类别>/<年>/<月>/<日>/<写入时刻>-<记录身份>.json`（UTC，写入时刻为 RFC 3339 的微秒形式，记录身份为 UUIDv7）。写入只新建，不覆盖已有的键；写入带这一类别的保留期。写入在对象存储答成功之后才算完成 | 向量 `run-profile`、SDK 测试 |
| P12.2 | 必须 | 记录是 JSON：`record_type` 为 `be.ops.run_profile_record`、`schema`、`deployment`、`kind`（类别）、`id`、`written_at`、`writer`（组件 ID 与实现实例）、`body`（类别规定的内容）、`signature`。`signature` 之外的部分按规范编码（[08](08-identity-authz-audit.md) 的规范形式）后，用写入者服务凭据的私钥签名；`signature` 带算法、签名值与写入者的证书链（PEM） | 向量 `run-profile`、SDK 测试 |
| P12.3 | 必须 | 类别与保留期（起始值，部署可加长不可缩短）：`generation.deployment`、`generation.authz`（恢复代次的推进，`body.value`）与 `trust.*`（信任材料的签发、轮换与吊销）10 年；`alert`（告警渠道的记录，P12.7）与 `recovery.step`（恢复中人工确认的步骤）不短于完整物理备份的保留，起始 30 天 | 向量 `run-profile`、SDK 测试 |
| P12.4 | 必须 | 读取一个类别：列出键前缀下的全部对象，逐条按 P12.2 核对签名；签名不成立、或写入者的证书链按信任材料历史不成立的记录不用，并告警。恢复代次的当前值是这一类别里签名成立的记录的最大 `body.value`，没有记录时为 0 | 向量 `run-profile`、SDK 测试 |
| P12.5 | 必须 | 推进一种恢复代次：新值 = 运行档案、证据存储与各库中见过的最大值 + 1；先把新值写进运行档案并得到成功，才写入各库与使用它。写不进运行档案时不推进，操作不开始（装配项目安全 03 的 AT62） | 向量 `run-profile`、SDK 测试 |
| P12.6 | 必须 | 运行档案的写入凭据只给需要写的执行者（恢复工具、授权成员、发告警的组件），与部署备份的凭据分开；凭据与秘密从不出现在记录里 | SDK 测试 |

## 告警渠道

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P12.7 | 必须 | 告警渠道的机器可读部分就是运行档案的类别 `alert`：记录者把签名的完整记录（P12.2，`body` 是原本要写进证据的记录）写进去；接收时刻取对象存储给出的写入时刻，不取记录自报的 `written_at`。通知值班的人另发一份到部署配置的 webhook（只通知，不作为恢复的依据） | SDK 测试 |
| P12.8 | 必须 | 写告警渠道与发 webhook 各有时限（装配项目协议 15 的参数，起始 2 秒），互不等待；运行档案那一份写不进时，本地记一条严重级别的“双通道失效”日志（`event` 为 `evidence_double_failure`，带记录身份与类别，不带记录正文中的个人信息），调用方照常继续：不能为了证据推迟收紧 | SDK 测试 |

## 证据

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P12.9 | 必须 | 证据记录是 `be.evidence.record`：`id`（UUIDv7，也写进属主的变更历史，“已体现”按它判断）、`recorder`（组件 ID 与实现实例）、`category`（装配项目协议 15 证据表的一行，取值见向量 `evidence-record`）、`phase`（`intent` 意图、`effective` 已生效、`cancelled` 已取消、`general` 一般）、`position`（属主库的纪元与提交序号；意图没有）、`subject`（主体，可缺）、`object`（类型、身份与提交前的版本）、`change`（变更本身，不是变更后的状态）、`at`。规范编码与摘要同安全记录（[08](08-identity-authz-audit.md) 的规范形式），摘要的前缀是 `be.evidence.record.v1` | 向量 `evidence-record` |
| P12.10 | 必须 | 证据存储按（`id`，`phase`）只收一次：同一对再来、摘要相同，答“重复”和原来的回执；摘要不同，答“冲突”，不保存，并告警。结论（`effective`、`cancelled`）与同一 `id` 的意图要有相同的记录者、类别、主体与对象，否则答“冲突”；没有意图的结论照收（意图可能只进了告警渠道） | 向量 `evidence-record` |
| P12.11 | 必须 | 记录者就是调用者：`recorder.component` 不是调用者的服务身份的，整批拒绝（`PERMISSION_DENIED`） | SDK 测试、组件测试 |
| P12.12 | 必须 | 回执在记录持久之后给出，带证据存储自己的位置（纪元与存储序号，只增）；一批里逐条回答：已收下、重复、冲突 | 组件测试 |
| P12.13 | 必须 | 列出：按存储位置升序，从给出的位置之后起，每页至多 500 条，可按记录者与类别筛选；只有部署配置的读者（恢复工具等）可以列出 | 组件测试 |
| P12.14 | 必须 | 证据存储不随整套恢复回退：恢复数据库的那一步不动它的库（装配项目协议 15 第 3 步）；它自己从备份恢复时，备份点之后的证据从告警渠道与运行档案补回，其余列入损失范围 | 恢复工具的测试 |
