# 阅读说明

## 规则的写法

每条规则一行：编号、层级、内容、检验。

| 列 | 含义 |
| --- | --- |
| 编号 | `P<章>.<序号>`，发布后不改不复用；废止的规则保留编号并标“废止” |
| 层级 | **必须**：从外部可观察，一致性套件检验；**应当**：建议，套件给出警告；**内部**：外部不可观察，官方 SDK 用自己的测试与静态检查保证，其他语言的组件书面声明并接受评审 |
| 检验 | 一致性套件的检查编号（`CK-<主题>-<序号>`），或“向量 `<文件>`”，或“SDK 测试” |

“组件”指一个组件进程，或外壳里的一个成员；“运行时”指 SDK 交给模块的那一层（官方 SDK 的实现，或其他语言组件自己的等价物）。时长写成毫秒或秒，必要时同时给出名称（例如“停止时限”）以便配置引用。

## 能力清单与功能矩阵

`capabilities.json` 把每条规则归入恰好一项能力（检查会拒绝没有归属或归属两处的规则，所以加规则时同时给它归属）。`owner` 为 `sdk` 的能力由每个 SDK 在自己仓库根目录的 `features.json` 中标出状态，这就是协议 18 的功能矩阵；`component`、`assembly` 的能力由组件与装配检查负责。`rules` 为空的能力只留形状，规则随后续章节加入。

| 状态 | 含义 | 组件能否声明 |
| --- | --- | --- |
| `verified` | 已实现；该能力的向量与检查在这个 SDK 的测试中通过（需要基础资源的对真实的 PostgreSQL 与消息系统运行） | 能 |
| `implemented` | 已实现，测试还不完整 | 能，装配检查给出警告 |
| `not_implemented` | 没有实现或只留形状 | 不能，装配准入拒绝 |

`features.json` 的每一项：`status`；`evidence` 是 SDK 仓库里证明它的测试名；`pending` 列出这项能力中尚未验证或尚未实现的规则与原因（例如要在真实镜像里验证的），不能借 `verified` 掩盖。

## 向量文件的格式

每个文件是一个 JSON 对象：

```json
{
  "topic": "outbound-timeout",
  "protocol": "3.0.0-alpha.26",
  "rules": ["P4.3"],
  "description": "…",
  "cases": [ { "id": "…", "…": "…" } ]
}
```

`id` 在文件内唯一，发布后不改；每个文件在自己的说明里写明 `cases` 的字段。实现读取全部 `cases`，逐条比较，一条不符就是缺陷。
