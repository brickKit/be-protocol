# 15 冷热转层

依据：装配项目协议 11（冷热转层）、数据与生命周期的冷热分层，A149–A154。属主组件的单元目录是唯一权威：一个归档单元从开放到封存、复制、校验、发布、释放在线层、销毁，每一步在属主的本地事务里裁决；对象存储与历史表只放副本，目录决定读哪一份。

首批两条路线（A150）：`postgres`（同库的历史行，SDK 的表 `be_tier_row`，温层）与 `object-parquet`（对象存储上的 Parquet 加清单，冷层，A149 的 parquet-go）。在线层本身的路由是 `online`。

## 单元与目录

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P15.6 | 必须 | 归档单元由（类别，分组，序号）标识，身份是属主生成的 UUIDv7。分组是分组列的值与起算期间（起算列的 UTC 年月）按规范编码（[08](08-identity-authz-audit.md) 的规范形式）写成的字符串；同一分组里后来才到终态的聚合进序号更大的单元。单元的成员在封存时写定（`be_tier_member`，每个聚合一行，记根的主键） | 向量 `tier-plan`、SDK 测试 |
| P15.7 | 必须 | 目录在组件自己的 schema 里（本仓库 `migrations/0017_tiering.up.sql`）：单元（`be_tier_unit`）、成员即定位索引（`be_tier_member`）、清单的各版本（`be_tier_manifest`）、保全（`be_tier_hold`）、读取租约（`be_tier_lease`）、目录版本（`be_tier_catalog`）与温层的行（`be_tier_row`）。单元的状态为 `open`、`sealed`、`published`、`released`、`destroyed`，转移只按协议 11 的状态表；改变路由或内容的每次提交（发布、释放、路线更换、擦除、销毁）把目录版本加一 | SDK 测试 |
| P15.8 | 必须 | **规范行**：一行是一个对象，键为列名，值按列的类型：文本按 NFC 的字符串；整数（2、4、8 字节）与 `numeric` 按规范十进制的字符串（[08](08-identity-authz-audit.md) 的十进制形式，所以不受 2^53 的限制）；布尔；`uuid` 为小写带连字符的字符串；`timestamptz` 为 UTC 微秒（`2006-01-02T15:04:05.000000Z`）；`date` 为 `YYYY-MM-DD`；`jsonb` 为源库给出的文本；`bytea` 为标准 base64。值为 null 的列不写（于是 null 与空字符串不同）。主键的规范形式是主键各列的值按列序组成的数组的规范编码 | 向量 `tier-digest` |
| P15.9 | 必须 | **单元的摘要**：每张表按主键的规范形式（字节序）排序，表的散列为按此顺序每行“8 字节大端的长度加规范行的字节”拼接后的 SHA-256；单元的摘要为 `be.tier.unit`、主版本 1 对 `{class, schema_version, tables: [{name, rows, sha256}]}`（表按名字排序，`rows` 为十进制字符串）的规范摘要（[08](08-identity-authz-audit.md) 的域分隔摘要）。摘要只取决于内容，与路线、文件的切分与列序无关；第三方可以从清单与文件算出同一个值 | 向量 `tier-digest` |
| P15.10 | 必须 | 摘要的版本（`digest_version`，现在为 1）与格式写进清单；改变规范行或摘要的算法是新的版本，旧版本的清单仍按旧版本核对 | 向量 `tier-digest` |

## 候选、封存与写屏障

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P15.11 | 必须 | **候选选择**由属主的转层作业在部署声明的低峰时段（`TIERING_WINDOW`）执行：对驻留期不为 `never` 的每个可转层类别，找出终态、且“起算时刻加驻留期”早于现在的聚合，按分组逐个尝试封存（P15.12）；封存条件不满足的留在在线层，下一轮再试，阻塞的原因记在目录。过了驻留期 30 天仍封存不了的告警，列出阻塞的聚合与原因（TR28、TR30）。哪些单元做什么由规划函数决定（P15.37） | 向量 `tier-plan`、SDK 测试 |
| P15.12 | 必须 | **封存**在属主的一个本地事务里：锁住候选的根行（`FOR UPDATE`，在锁下重新求终态条件）；组件登记的阻塞检查（例如未结束的预占、未关闭的期间、未对账的引用）都答“无”；没有指向这些根的未发布事件与未完成的工作项；然后写成员、计算摘要与成员数、最晚的起算与创建时刻，状态转为 `sealed`。任何一项不满足，整个分组这一轮不封存，原因写在单元上（迁移 0018 的 `blocked`），`blocked_since` 记它到期的时刻（候选中最晚的起算时刻加驻留期），告警从那里算 30 天（TR01、TR23、TR30） | SDK 测试 |
| P15.13 | 必须 | **写屏障**：SDK 在迁移时为每个可转层类别的根表与子表建触发器（幂等）：插入、更新或删除的行属于一个成员、而成员的单元不是 `open` 时，触发器抛 SQLSTATE `BE001`，按向量 `db-errors` 映射为 `RECORD_SEALED`（409，不重试）；子表的触发器先对它的根行取 `FOR SHARE` 锁，所以与封存的 `FOR UPDATE` 串行：封存先提交，迟到的写入被拒；写入先提交，封存在锁下看到它（TR03）。被拒的写入由业务写成更正记录，放在开放的聚合里、引用被更正的记录（TR02）。写屏障不依赖写入从哪个入口来。SDK 自己对一个单元的写（释放、销毁、擦除）在事务里把 `be.tier_unit` 设成这个单元的身份（事务级），触发器只对这个单元的成员放行 | SDK 测试 |

## 转层：认领、复制、校验与发布

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P15.14 | 必须 | 转层工作项（[07](07-work.md)）在一个本地事务里**认领**单元：代次加一，记下认领时数据库的纪元（[06](06-events.md) 的 P6.7），工作者带着（代次，纪元）往下做 | SDK 测试 |
| P15.15 | 必须 | **复制**在数据库事务之外进行：按成员读出封存的行（在一个只读的可重复读快照里），写到目标路线。`object-parquet`：对象的键为 `<组件前缀>/<类别>/<单元>/<代次>.<清单版本>/<表>-<序号>.parquet`，只新建、不覆盖（条件写入）；`postgres`：写进 `be_tier_row`，带清单版本，发布之前不被读取 | SDK 测试 |
| P15.16 | 必须 | **清单** `be.tier.manifest`（规范 JSON，`schema` 1.0）：单元、类别、版本、路线、代次与纪元、格式（`parquet-1` 或 `pg-rows-1`）、类别的结构版本、摘要版本与摘要、每张表的名字、主键列、列（名字、类型、可否为空）、行数与对象（键、行数、字节数、SHA-256）、写成时刻。`object-parquet` 的清单另写一个对象 `<…>/manifest.json`，第三方读取器按它读文件 | 向量 `tier-manifest`、SDK 测试 |
| P15.17 | 必须 | **校验**完整读回目标副本：每张表的行数、每个子行的根都在、按规范行重算的摘要等于封存时的摘要、定位与授权要用的列都在、每个对象的 SHA-256 与字节数等于清单。任何差异都不发布：源数据保留，工作项失败并告警（TR05） | SDK 测试 |
| P15.18 | 必须 | **发布**在属主的一个本地事务里：单元仍为 `sealed`（路线更换时为原状态与原清单版本，P15.35）、代次与纪元等于工作者认领时得到的值、纪元仍是当前的纪元、摘要没有变；然后写清单的新版本、路由改到目标路线、状态转为 `published`、目录版本加一。不满足的被拒绝：旧代次或旧纪元的工作者不能改变目录，它写下的对象成为孤儿（TR04） | SDK 测试 |

## 读取

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P15.22 | 必须 | **按身份读**：经成员表找到单元，按它的路由读；`online` 照常读在线表。路由指向 `postgres` 或 `object-parquet` 而行或对象缺失、读不出或 SHA-256 不符时，原因 `DEPENDENCY_UNAVAILABLE`（503，可重试，`metadata.dependency` 为 `blob` 或 `db`）并告警，不回答“不存在”（TR08、TR09） | SDK 测试 |
| P15.23 | 必须 | 列表的默认范围是“未关闭，或最近 N 天内创建”；只有调用方明确请求历史时才读在线层以外的路线（TR10） | SDK 测试 |
| P15.24 | 必须 | **目录快照**：一次列表或导出在开始时读目录版本，此后每个单元只按这个版本的路由读一次：在线的查询排除在这个版本时已不在在线层的单元的成员，其余单元按它们在这个版本的路由读。游标绑定目录版本；翻页时目录变了，按快照继续，快照要的数据已经不在（释放或清理之后）时答 `QUERY_PLAN_CHANGED`，要求重新开始，不跳到另一套集合（TR07） | SDK 测试 |
| P15.25 | 必须 | **读取租约**：读在线层以外路线的列表与导出在开始时登记租约（目录版本、用途、到期，起始 15 分钟，读的过程中续期），结束或过期时失效 | SDK 测试 |
| P15.26 | 必须 | **冷读的限度**：读历史（在线部分加离开在线层的单元）的同步读有时限（`TIERING_COLD_SYNC_LIMIT`，起始 10 秒）；冷单元的读取在成员内有并发上限（`TIERING_COLD_CONCURRENCY`，起始 4），等不到名额也计入时限。时限内读完才答完整结果；超过的转成异步导出（答 202 与导出的身份），不返回部分数据；能力不足以完整完成的答 `QUERY_NOT_COMPLETABLE`（TR11）。冷读按**当前**的授权求值（段与字段掩码，[08](08-identity-authz-audit.md)），不因游标绑定旧的快照而保留访问（TR12）；读取由属主登记的读取器执行（授权的操作、从根求事实、输出的塑形、在线部分的读取），不接受调用方的 SQL 或对象地址 | SDK 测试 |
| P15.38 | 必须 | **异步导出**：导出记在 `be_tier_export`（迁移 0020：身份、类别、请求者、参数、状态 `pending`／`done`／`failed`、对象键、行数、失败原因、建立、完成与到期），由队列作业 `be.tiering.export` 执行：运行时取新的目录快照与租约，按请求者在**运行时**的授权读两部分，写成 NDJSON（每行一个输出对象，与同步读答的对象相同的 JSON：被掩码的字段为 null，P8.31）放在冷层存储的 `<前缀>/exports/<身份>.ndjson`（不覆盖），完成时记行数与到期（起始 7 天）；最后一次尝试仍失败的记为 `failed`（`INTERNAL`），请求者不会看到它一直未完成。导出的状态只答请求者本人（别人答 `NOT_FOUND`），完成的附预签名的读取地址（读的凭据，起始 15 分钟有效）。到期的导出由清理删除对象与行。没有冷层存储、存储开了对象锁（导出含个人信息，到期要删）或类别没有读取器时，要转异步的读答 `QUERY_NOT_COMPLETABLE` | SDK 测试 |
| P15.27 | 必须 | **解冻**：把一个单元复制到只读的临时区（`be_tier_row` 里版本 -1 的行，`be_tier_thaw` 记到期，起始 30 天，迁移 0019），按身份读时优先读它，不重开原业务的写入（TR18）；到期后由清理删除 | SDK 测试 |

## 保全、保留、销毁与擦除

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P15.28 | 必须 | **保全**是独立的记录（`be_tier_hold`）：范围（单元、类别或一个聚合）、来源（法律、审计、纠纷）、授权人与理由、开始与解除；设置与解除要类别声明的保全操作（`hold_operation`）的授权，由 SDK 检查，授权人记主体。保全与状态正交：只挡销毁与会丢内容的擦除 | SDK 测试 |
| P15.29 | 必须 | **销毁**由工作项在一个本地事务里决定：先对保全表取 `SHARE` 锁（同时设置的保全要等这个事务结束，TR14），再检查保留已到期（最短保留已过）、没有覆盖它的生效保全（TR13）、有生效的销毁批准、保留类别不是 `pending`；然后写销毁的证据（[12](12-evidence-and-run-profile.md) 的两段写，类别 `destruction`：意图在决定事务之前，核对不过时取消）、状态转为 `destroyed`、写墓碑（范围、摘要、依据与时刻）、目录版本加一；提交之后删除对象、温层的行、在线的行与解冻的副本（可以重做）。成员表保留：按身份读已销毁的记录答 `NOT_FOUND`。**批准**记在 `be_tier_approval`（迁移 0021：范围 `unit` 或 `class`、批准人、理由、时刻、撤回）：`class` 的批准是常设的（例如审计记录按保留期删除），撤回后不再生效；批准与撤回要类别声明的批准操作（`approve_operation`）的授权。属主的作业 `be.tiering.destroy` 每天对规划函数答 `destroy` 的单元执行 | SDK 测试 |
| P15.30 | 必须 | 销毁与擦除的证据由属主的重放函数在整套恢复中重新执行（[12](12-evidence-and-run-profile.md) 的 P12.19–P12.22：恢复点之后的销毁再做一次，TR16）；只有意图的列复核，不自动执行 | SDK 测试 |
| P15.31 | 必须 | **擦除**（装配项目协议 07 的个人信息擦除）：`open` 的单元按业务擦除在线的行；`sealed` 的单元擦除在线的行后在同一事务里重新计算摘要，进行中的转层因摘要变了而发布失败、重做（TR27）；`published` 与 `released` 的单元生成擦除后的副本与新的清单版本（P15.15–P15.18 的同一个发布规则，状态不变），旧版本的对象与行在保全与恢复规则允许后清理；解冻的副本在新版本发布时删除。擦除的是类别声明的可擦除列（根与它的子行，置空）。擦除的证据（类别 `erasure`）记下旧摘要与依据，两段写同销毁：意图在前，结论在发布（或 `sealed` 的那个）事务里，那个事务对保全表取 `SHARE` 锁再核对一次保全。有生效的保全时，会丢失内容的擦除推迟并告警（TR15），不写意图。整套恢复里重放的擦除：`sealed` 的在重放事务里重做；`published` 与 `released` 的由属主的队列作业 `be.tiering.erase` 在开放后重写新版本 | SDK 测试 |
| P15.32 | 必须 | 开了对象锁（合规模式）的路线不能接收声明了可擦除列的类别：发布之前拒绝并告警 | SDK 测试 |
