# 01 生命周期与健康

依据：装配项目协议 17 的“启动与停止”“外壳义务”“健康检查”，协议 14 的“库内计数与纪元”第 7 条（本地提交持久），安全 03 的计时源。

## 入口与端口

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P1.1 | 必须 | 组件镜像有两个入口，由第一个参数选择：`serve`（缺省）启动服务；`migrate` 执行结构迁移后退出。未知的入口参数以退出码 64 退出 | CK-LC-01 |
| P1.2 | 必须 | `migrate` 成功时退出码 0；连续执行两次都成功（第二次没有可做的事）；失败时退出码非 0，并在最后一行日志写明失败的迁移 | CK-LC-02 |
| P1.3 | 必须 | 用户面 HTTP 监听在平台给的端口：单独运行时取 `PORT`，在外壳里取该成员配置的 `httpPort`。系统面 gRPC 监听在组件清单 `deployment.extraPorts` 中名为 `grpc` 的端口（外壳里取成员配置 `extraPorts` 中同名的一项）。两个端口都监听全部接口 | CK-LC-03 |
| P1.4 | 必须 | 声明的每个端口在“就绪”时都真的在监听 | CK-LC-04 |
| P1.19 | 必须 | 两个端口接受的连接关闭 Nagle 算法（`TCP_NODELAY`）。一个回答常分几次写出（头与正文），开着 Nagle 时后一段要等对方的延迟确认（Linux 上约 40 毫秒），保持连接上的每个请求都慢这么多，与处理耗时无关 | CK-LC-14 |
| P1.20 | 必须 | 用户面 HTTP 的保持连接：服务端的空闲超时不短于 120 秒，并且长于调用方客户端的空闲超时（SDK 的出站客户端 90 秒）。服务端先关闭空闲连接时，客户端可能恰好在关闭的那一刻重用它，请求以连接被关闭（EOF）失败；POST 这类不能自动重试的请求就成了错误。实测：Python 服务端用 uvicorn 默认的 5 秒、客户端 90 秒时，单核跑满、连接数涨落的 200/s 下 2000 次里有 2 次 | SDK 测试 |

## 健康与就绪

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P1.5 | 必须 | `GET` 与 `HEAD` `/healthz`（用户面端口）在进程存活期间回答 200，正文为空或 `ok`；**从不**检查数据库、消息系统、授权或其他组件；“启动中”“停止中”也回答 200 | CK-LC-05 |
| P1.6 | 必须 | `GET` 与 `HEAD` `/readyz` 在“就绪”与“恢复就绪”时回答 200（探针可能用 `HEAD`，例如 GNU wget 的 `--spider`；RFC 9110 要求通用服务器在支持 `GET` 的地方支持 `HEAD`）；其余状态回答 503 与错误对象（reason `NOT_READY`，[03](03-errors.md)），`metadata.state` 写当前状态（`starting`、`stopping`）。外壳的 `/readyz` 在全部成员就绪后回答 200，否则 `metadata.waiting` 列出还在等的成员组件 ID（逗号分隔） | CK-LC-06 |
| P1.7 | 必须 | `/healthz`、`/readyz` 与自描述端点不经过认证、授权与限流，不写访问日志的 INFO 行（只计数） | CK-LC-07 |
| P1.8 | 必须 | `GET` `/.well-known/be-component` 回答 JSON：`component_id`、`version`、`protocol`（本协议版本）、`sdk`（实现名与版本，非官方语言写自己的）、`capabilities`（声明的能力名列表，安全 09b）。外壳回答外壳自己的，另加 `members`：每个成员的同样字段 | CK-LC-08 |

## 启动

状态：`starting` → `ready`（或恢复模式下的 `recovery_ready`，P1.22）→ `stopping` → 退出。

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P1.9 | 必须 | 配置不合法时，在打开任何端口之前退出，退出码 78，并一次报出全部错误（[02](02-configuration.md) 的 P2.6） | CK-CF-03 |
| P1.10 | 必须 | 启动时检查数据库的持久设置：`fsync` 为 `on`，`synchronous_commit` 为 `on`、`remote_write` 或 `remote_apply`；不合格时不进入就绪，以退出码 69 退出，日志写明实际值 | CK-LC-09 |
| P1.11 | 必须 | 启动时检查计时源：有效期按计入系统挂起的单调时钟计算（Linux 的 `CLOCK_BOOTTIME`）；拿不到时以退出码 69 退出 | SDK 测试 |
| P1.12 | 必须 | 进入就绪时写一行日志，`event` 为 `ready`，带组件 ID、版本、协议版本与启动耗时（毫秒） | CK-LC-10 |
| P1.13 | 内部 | 外壳中成员按依赖顺序初始化；任何成员初始化失败，外壳不进入就绪，按 P1.16 退出并点名成员 | SDK 测试 |
| P1.21 | 内部 | 进程里的 SDK 版本不早于外壳任何成员要求的最低版本。由构建保证的语言（Go：模块图对 SDK 只取一个版本，取各成员要求的最高版本）不必在启动时再查；构建不保证的语言（Python：外壳用 `override-dependencies` 统一 SDK，可以指定得比成员的要求旧），外壳启动时核对每个成员在包元数据里声明的最低版本（`Requires-Dist: be-sdk>=<版本>`），没有声明或进程里的 SDK 不满足的，拒绝启动（退出码 78），点名成员、它的要求与进程里的版本 | SDK 测试 |

## 恢复模式

整套恢复（装配项目协议 15）期间，部署按阶段只运行允许的部分。阶段经部署级配置键下发，换阶段就重启（BrickKit 没有热加载：改配置再 `brickkit up`）。

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P1.22 | 必须 | `RECOVERY_PHASE`（[02](02-configuration.md)，进程级）有值时，成员以恢复模式启动，进入“恢复就绪”（`recovery_ready`）而不是“就绪”：`/readyz` 回答 200，正文 `{"state":"recovery_ready","phase":"<阶段>"}`（就绪探针据此把它当作可以路由：恢复中系统面要能调用，例如补发）；自述（P1.8）多一个字段 `recovery_phase`；就绪日志（P1.12）带 `phase`。外壳的阶段是成员共同的那一个 | SDK 测试 |
| P1.23 | 必须 | 各阶段运行什么（不在表里的取值按 [02](02-configuration.md) 的 P2.6 是配置错误）：<br>`frozen`（冻结，协议 15 的第 2–4 步）：用户面除健康、就绪与自述之外的请求答 `MAINTENANCE`（[03](03-errors.md)）；发件转发、订阅、后台工作（含 SDK 自带的作业）都不运行；系统面照常。<br>`redelivering`（重建消息流，第 5 步）：用户面同上；发件转发与订阅运行（补发与投影）；后台工作不运行；系统面照常。<br>`replaying`（证据的重放，第 6 步）：与 `redelivering` 相同；重放经系统面的 `ReplayService`（[12](12-evidence-and-run-profile.md) 的 P12.19），不经后台工作。身份成员在这三个阶段都不签发令牌、不发布公钥集合（装配项目协议 15 的恢复模式表）。<br>第 7 步以后的阶段随那些步骤加入 | SDK 测试 |
| P1.24 | 必须 | 恢复模式不改变一个成员“只读自己的库”的做法：阶段只决定哪些部分运行，不在库里留状态；所以第 3 步恢复数据库不会把阶段一起回退 | — |

## 停止

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P1.14 | 必须 | 收到 `SIGTERM` 或 `SIGINT`：立刻转入 `stopping`，`/readyz` 回答 503；先等待“摘除延迟”（起始值 2 秒，让负载均衡与服务发现先摘掉这个实例），再关闭监听、拒绝新请求；然后等处理中的请求完成，执行中的工作项完成当前事务并释放租约，消费者停止拉取 | CK-LC-11 |
| P1.15 | 必须 | 停止时限（起始值 30 秒，从收到信号起算，含摘除延迟）内完成则退出码 0；到时强制退出，退出码 1。正确性不依赖停止流程完成（租约到期后由接替者接管） | CK-LC-12 |
| P1.16 | 必须 | 进程作为容器的 1 号进程运行时，也按 P1.14 响应 `SIGTERM`（自己安装信号处理；不能依赖默认动作，1 号进程没有默认的终止动作） | CK-LC-13 |
| P1.17 | 内部 | 外壳的停止宽限不小于任何成员的；成员并行停止；遥测导出器在全部成员停下之后才关闭 | SDK 测试 |
| P1.18 | 内部 | 模块代码从不退出进程：不调用退出、不写致命日志、不在后台协程里抛出未捕获的异常；退出只由启动器决定 | SDK 静态检查 |

## 退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 正常停止；`migrate` 成功 |
| 1 | 运行中失败，或停止时限到强制退出 |
| 64 | 入口参数不认识 |
| 69 | 启动检查不合格（数据库持久设置、计时源） |
| 78 | 配置不合法 |

外壳拒绝启动（成员没编进来、版本不同、进程里的 SDK 早于成员的要求（P1.21）、共享配置不一致、任何成员的配置不合法）同样用 78，日志一次列出全部原因并点名成员（协议 17 的外壳义务）。
