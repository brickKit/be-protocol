# 06 事件：信封、发件表与运输

依据：装配项目协议 02 的 S2（信封字段的唯一清单）、“来源一侧编号、纪元与补取”的第 2、3 步、“接收规则”与参数起始值；协议 14 的“库内计数与纪元”；协议 15 的“发件表的保留与消费者进度”；“事务与消息”“消息运输与事件信封”。本章写生产者一侧（发件表、锁内编号、纪元、转发）、运输端口与两个适配器、消费者的去重、死信与大消息。水位来源的回声、补取与消费者的连续位置、对齐随后续任务加入本章。

## 流、分区与发件表

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.1 | 必须 | 事件属于一个**流**（契约中声明的名字，小写字母、数字、下划线与点，例如 `erp.inventory.stock`），流声明分区数（1–256，发布后不改）。一条记录的事件只进一个分区：分区 = FNV-1a 64 位（记录身份的小写规范字符串的 UTF-8 字节）对分区数取余；唯一的例外是水位来源的回声行，每个分区一条（[09](09-lists-search-projections.md) 的 P9.16） | 向量 `partition` |
| P6.2 | 必须 | 业务写入与发件行在同一个本地事务中提交（经 [05](05-database.md) 的事务入口）；发件行不在事务外写，也不先发后写 | CK-EV-01 |
| P6.3 | 必须 | 发件表、分区计数行、纪元历史与部署恢复代次都在组件自己的 schema，由 SDK 的迁移建立（本仓库 `migrations/`）；表的形状对三种语言相同 | CK-DB-05 |
| P6.4 | 必须 | 每条发件行在写入时得到：事件身份（UUIDv7）、流、分区、插入顺序（库内序列）、事件类型、记录身份与版本、投影语义（`full`、`partial`、`delete`）、法人（交易事实）、受影响的主体（水位来源）、因果（上一个事件的身份）与跳数、追踪上下文、载荷，以及**行摘要** = SHA-256（事件身份的规范字符串、一个 0 字节、载荷字节）的小写十六进制；发布位置与纪元在编号时才写 | 向量 `envelope` |

## 锁内编号与纪元

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.5 | 必须 | **提交后编号**：每个（流，分区）一行计数。编号事务先锁计数行，取得锁之后用新的语句快照选出可见、尚未编号的发件行，按插入顺序编连续的发布位置（从计数加一起），与计数一起提交。事务内不做网络调用；锁等待 2 秒、整个事务 5 秒（PostgreSQL 17 起用 `transaction_timeout`，更早用 `statement_timeout` 加 `idle_in_transaction_session_timeout`），超时回滚 | CK-EV-02 |
| P6.6 | 必须 | 两个副本（或转发与补取）同时编号时，发布位置不重复、不跳号；回滚的行从不可见，不留空洞；长事务只推迟它自己的行 | CK-EV-02 |
| P6.7 | 必须 | **纪元** =（部署恢复代次，当前写入时间线），按这个顺序比较。部署恢复代次存在组件 schema 的单行表 `be_recovery_generation`（安装时 1，使库内容回退的操作在解冻前推进它）；时间线取当前 WAL 文件名的前 8 位十六进制。SDK 的迁移提供易变函数 `be_current_db_epoch()` 读取二者 | CK-EV-03 |
| P6.8 | 必须 | 编号事务读到的纪元与计数行记录的不同时，在纪元历史 `be_epoch_history` 中写下（流，分区，旧纪元，分叉点 = 旧纪元保留下来的最后位置，新纪元），新纪元的位置从 1 开始；读不到代次或时间线（例如在只读副本上）时拒绝编号 | CK-EV-03 |
| P6.9 | 必须 | 发布位置写作（实现实例，纪元，序号）。实现实例是安装时生成的随机身份，由配置键 `IMPLEMENTATION_INSTANCE` 提供（UUID，成员级；产生事件的组件必填），不存库、不随库恢复改变 | 向量 `envelope` |

## 转发

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.10 | 必须 | 转发按位置顺序发布已编号、未发布的行，等运输的持久确认之后才标记为已发布；确认丢失时再发一次（至少一次）。消息身份 = 事件身份，运输在去重窗口内据此去重 | CK-EV-04 |
| P6.11 | 应当 | 转发按（流，分区）取租约以减少争用；租约不承担正确性：停顿后恢复的旧持有者也只能排队取编号锁，重复发布由消费者去重。持有者在租约过半之前不必重取（按自己的时钟从请求租约之前算起）；编号与读取已编号、未发布的行可以在同一个事务里 | SDK 测试 |
| P6.29 | 应当 | 业务事务提交后，同一进程里这个成员的转发立即开始转发，不等下一次轮询；轮询只兜底别的副本写入的行与失败后的重试。只在提交之后唤醒：事务内唤醒时新行还不可见。没有唤醒时，低负载下每个事件都要等半个轮询间隔（起始 250 毫秒的轮询下实测约 120 毫秒），负载越低反而越慢。唤醒只转发这些提交写过的（流，分区），轮询按自己的间隔走全部分区；唤醒不推迟轮询，否则持续的提交下轮询永远不来，别的副本的行没人转发。每次唤醒都走全部分区时，每个事件要付全部分区的租约、编号与读取（4 个分区约 25 个事务） | SDK 测试 |
| P6.32 | 应当 | 轮询先用一条只读语句找出有未编号或已编号未发布的行的（流，分区）（走未编号与未发布两个部分索引），只对这些分区取租约、编号与读取；没有这样的行的分区这一轮不开事务、不取租约、不写计数行。轮询的间隔与 P6.29 的唤醒不变（唤醒本来就只走它写过的分区），延迟不变；别的副本的行与待重试的行都是未发布的行，照旧由轮询找到。纪元变化写进历史（P6.8）推迟到那个分区下一次编号，那时读到的计数与纪元与原来相同，写下的历史一样。空分区每次轮询都做一个完整的编号事务时，12 个组件的业务链空闲着，8 个发事件的组件每个每秒约 17 个这样的事务，占数据库全部语句的 85–90%（2026-10-28 实测） | SDK 测试 |
| P6.12 | 必须 | 已发布的行按补发保留（装配项目协议 15 的参数，起始 7 天）保留，与消费者是否确认无关；超过的由 SDK 自带的 singleton 作业 `be.outbox.purge`（每小时）删除，未发布的行从不删除；作业在分区的计数行上记下删到的最大位置（`purged_generation`、`purged_timeline`、`purged_seq`，迁移 0014），补发据此判断是否超出保留（P6.38）；未发布的积压单独度量与告警 | CK-EV-05 |

## 信封

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.13 | 必须 | 信封用 CloudEvents 1.0 二进制模式：每个属性一个消息头，名字为 `ce-` 加属性名；载荷就是业务对象（JSON），`ce-datacontenttype` 为 `application/json`。属性与消息头见下表；消费者不认识的扩展属性原样保留、不报错 | 向量 `envelope`、CK-EV-09 |
| P6.14 | 必须 | 消息头连同载荷有大小上限；载荷超过 64 KiB 时放进对象存储：生产者在转发时（事务外）把载荷写到自己的桶与前缀下的 `<前缀>events/<事件身份>`，事件的载荷换成引用对象 `{"claim":{"uri":…,"size":…,"sha256":…}}`，`ce-beclaim` 为 `true`；`ce-bedigest` 仍是原载荷的行摘要（P6.4），订阅者取回对象后按它核对。`uri` 是这个对象的预签名只读地址（GET），有效期等于运输保留（7 天，也是 S3 签名第 4 版的上限）；再次发布（补发）时重新签发。订阅者用普通的 HTTP GET 取回，不持有生产者的存储凭据，核对大小与摘要，不符按处理失败。`uri` 的主机是生产者配置的对象存储地址，签名覆盖主机名，订阅者不能换成自己知道的别名：所以一个部署里每个组件的 `OBJECT_STORE_URL` 必须用同一个主机名，并在每个组件所在之处都解析到同一个存储（容器、Pod 与本机进程混在一起时，不能一边叫 `host.docker.internal`、一边叫 `localhost`；否则大载荷的事件在两边之间取不到，重试用完后成为死信）。对象的保留不短于运输保留、补发保留与最长对齐时长三者中最长的一个，由部署的生命周期规则负责（装配项目协议 12、15） | CK-EV-06 |
| P6.15 | 必须 | 处理一个事件时产生的新事件带 `becausation` = 该事件的身份、`behops` = 它的跳数加一；跳数超过 10 时按处理失败，不发出（成环的因果链在跳数上限处截断） | CK-EV-07 |

| 属性（消息头 `ce-<属性>`） | 必有 | 内容 |
| --- | --- | --- |
| `specversion` | 是 | `1.0` |
| `id` | 是 | 事件身份 |
| `source` | 是 | `urn:be:<产生方组件 ID>` |
| `type` | 是 | 事件类型（契约中声明，带主版本，例如 `erp.inventory.stock_moved.v1`） |
| `time` | 是 | 写发件行时的 UTC 时刻，RFC 3339，毫秒 |
| `subject` | 是 | 记录身份 |
| `datacontenttype` | 是 | `application/json` |
| `bestream`、`bepartition` | 是 | 流与分区 |
| `beimpl` | 是 | 实现实例 |
| `beepoch` | 是 | 纪元，写作 `<代次>.<时间线>`（十进制） |
| `beseq` | 是 | 分区内的发布位置（十进制） |
| `beversion` | 是 | 记录版本（十进制） |
| `beprojection` | 是 | `full`、`partial` 或 `delete` |
| `bedigest` | 是 | 行摘要（P6.4） |
| `behops` | 是 | 跳数，起点 0 |
| `becausation` | 否 | 上一个事件的身份 |
| `belegalentity` | 交易事实 | 法人 |
| `besubjects` | 水位来源 | 受影响的主体：JSON 字符串数组，最多 1,000 个 |
| `beclaim` | 否 | `true` 表示载荷是对象存储引用（P6.14） |
| `traceparent`、`tracestate` | 否 | W3C 追踪上下文（CloudEvents 分布式追踪扩展） |

## 运输端口

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.16 | 必须 | 运输由 `BUS_URL` 的 scheme 选择：`nats://` 为 NATS JetStream，`pgqueue://` 为 PostgreSQL 队列。同一条运输链的生产者与全部订阅者用同一个总线 | CK-BUS-01 |
| P6.34 | 必须 | 启动时连不上运输（连接被拒、超时、没有可用的服务器）不退出：保持“启动中”并每秒重试，直到连上或收到停止信号（此时退出码 0），与连不上数据库时一样（P5.10）。运输拒绝凭据、`BUS_URL` 不可用（scheme 不对）时以 78 退出；PostgreSQL 队列的库不存在时以 69 退出。基础资源与组件同时开机、运输晚到时，组件等它而不是退出后靠平台重启 | CK-BUS-10 |
| P6.35 | 内部 | 转发读一个分区已编号、未发布的行，沿 `(stream, partition, epoch_generation, epoch_timeline, seq)` 上只含这些行的部分索引按位置顺序取前一批，不走过保留期里已发布的行（P6.12，起始 7 天），也不把未发布的行全部取出再排序。违反时每批的代价随保留的行或积压增长：2 万条已发布的行在前时，按 `(stream, partition, seq)` 的索引每批 500 条约 3.4 ms，按位置顺序的索引约 0.6 ms（2026-11-02）；消息系统中断、未发布的行积压时，每批都要排整个积压 | SDK 测试 |
| P6.17 | 必须 | 主题 = `be.<流>.<分区>.<事件类型>`。JetStream 中每个流一个 stream（名字 `BE_` 加流名，点换成下划线、大写），主题 `be.<流>.>`，文件存储；生产者启动时与订阅建立时都确保它存在（订阅方可能先于任何生产者启动），设置相同，已存在时不改它的设置 | CK-BUS-02 |
| P6.18 | 必须 | 订阅是持久的，名字 = 订阅方组件 ID 加订阅名（`/`、`.`、`-` 换成下划线）。同一订阅的多个实例竞争领取，每条消息由其中一个处理；不同订阅（包括同一外壳的两个成员）各收一份。建立订阅幂等，已存在时不改它的设置 | CK-BUS-03 |
| P6.19 | 必须 | 处理成功并且业务写入已提交之后才确认；处理失败时否认，按退避重投（起始 1 秒，每次加倍，上限 30 秒）；未确认的消息在确认等待（30 秒）后重投；处理中的消息可以续期，防止慢消息被重投 | CK-BUS-04 |
| P6.20 | 必须 | 投递次数达到上限（3）仍失败的消息进死信：订阅方在自己的库里记一条死信（同一订阅、同一事件身份只一条），然后终止这条消息的投递；死信由查询与人工处理接管，不依赖“下一次投递” | CK-BUS-05 |
| P6.21 | 必须 | 消息头在运输中往返不变；超过运输上限的消息发布时明确失败，不截断 | CK-BUS-06 |
| P6.22 | 必须 | 尽力而为的通知（缓存失效之类）不存储、不重投；订阅者离线时错过 | CK-BUS-07 |
| P6.23 | 必须 | PostgreSQL 队列：表在总线库自己的 schema（本仓库 `migrations-bus/`）。消息按（事务号，库内序号）排列，订阅的读取位置也是这一对；读取者只读事务号低于 `pg_snapshot_xmin` 的行（低于它的事务都已结束，之后也不会再出现更小的事务号）。只按序号加 xmin 屏障不够：事务号较小、序号较大的行先提交时，位置会越过一个仍在途、序号较小的行，那一行之后提交也不会被读到，而且不报错 | CK-BUS-08 |
| P6.24 | 内部 | 两个适配器跑同一组运输检查；对一个会丢确认的假适配器跑这组检查必须失败 | SDK 测试 |
| P6.27 | 必须 | 消息系统只是运输缓冲：消息按运输保留（起始 7 天，与补发保留相同）删除，与订阅是否读到无关。JetStream 的流建立时设 `MaxAge`（已存在的流按 P6.17 不改，在这条规则之前建立的流由运维设定）；PostgreSQL 队列由打开运输的每个进程每小时删除超过保留的消息与指向它们的投递（删除幂等）。离线超过保留的订阅者从流里丢失这段事件，靠发件表的补发与对齐恢复（装配项目协议 15、协议 02） | CK-BUS-09 |
| P6.28 | 内部 | PostgreSQL 队列取一条消息的代价不随积压或别的流的消息量增长：领取只看到期的与租约过期的投递，两条路各沿一个按位置排序、只含那一类投递的部分索引（就绪的、在途的）取第一条，与统计信息新旧无关；领取的语句用缓存的通用计划，积压突然到来、统计落后时由 P5.33 的统计维护让计划重做（通用计划可能在积压还小时定下、积压到来后沿用，又取出全部积压再排序）；不为清理扫描全部积压（消息已被保留期清理掉的投递，在领到时丢弃）；读取位置有进展时立刻继续推进，只有既没推进也没领到消息时才等一个轮询间隔。每条消息只付领取与结果两次往返：先领取，领不到才推进读取位置（一次推进排进一批投递，由之后的领取分摊）；投递次数用尽、租约已过期的投递按间隔清理，领取不取它们，所以清理晚一点也不会多投一次（P6.20）。违反时积压越多每条越慢，订阅一旦落后就追不上；总线由全部流共用，别的流流量大时订阅也会被拖住 | SDK 测试 |
| P6.30 | 应当 | PostgreSQL 队列：一条新消息的插入提交之后（重复的消息身份不算新消息），用一条单独的语句 `NOTIFY` 通道 `be_bus_wake`，载荷为流名，每条新消息一次、不合并（每次通知唤醒一个读取者）。这条语句由传输在发布的路径之外发出：按顺序发布的转发器若要等它，每条消息多一次往返（实测 Python 发布方 200/s 时发布 p50 从约 13 ms 到约 19 ms）；待发的通知有上限，超出时丢掉，由轮询读到。不在插入的事务里发：发通知的事务在提交时取全实例的通知锁，并持有到提交记录写盘完成，这样的发布只能一个接一个提交（实测 8 个并发的发布约 435 次/秒，不发通知约 2000 次/秒）；只发通知的语句不写盘，持锁很短。通知失败不算发布失败（消息已存下，由轮询读到）；打开运输的每个进程用一条专用连接 `LISTEN` 它，收到时唤醒订阅了这个流、正在空闲等待的读取者，别的订阅不被唤醒。轮询照旧兜底：监听连接断开（重连之前）、连接池代理的事务模式下 `LISTEN` 不可用、被 xmin 屏障挡住的行（P6.23），都由下一次轮询读到。没有唤醒时，低负载下每条消息要等半个轮询间隔（100 毫秒的轮询下实测到达 p50 约 55 毫秒，NATS JetStream 约 3 毫秒） | SDK 测试 |
| P6.31 | 应当 | 每个订阅同时处理的条数，由部署方按成员设 `BUS_SUBSCRIPTION_CONCURRENCY`（[02](02-configuration.md)）。组件把依赖到达顺序的订阅声明为按顺序处理，这类订阅**整个订阅（所有实例合起来）同一时刻只有一条在处理**，按位置顺序；一条在等重投时，它后面的也等着（JetStream：持久订阅的在途上限为 1；PostgreSQL 队列：认领经订阅行串行、只取最早的一条）。是否按顺序随实例给出（与并发度一样），同一订阅的实例要一致：把已有的订阅改成按顺序处理时换一个订阅名（已有的持久订阅保留原设置，P6.18）。生效值：声明为按顺序时为 1；否则为配置值；未配置时为组件声明的值；都没有时为 1。缺省的 1 让同一实例内按到达顺序处理；调大后吞吐提高、订阅进程与数据库的 CPU 随之上升，消息之间不再有顺序（运输本来不保证顺序，多个副本竞争领取时也是这样）。只在订阅时读取，改了配置在重启后生效 | SDK 测试 |

## 进度与补发

整套恢复要按每个消费者在恢复点的进度补发（装配项目协议 15 的第 5 步），只回退了消费者自己的库时也一样。进度在消费者的库里，生产者不需要知道有哪些消费者。

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.36 | 必须 | 收件表每行另记产生方组件（信封的 `source` 去掉 `urn:be:`）与事件在来源的位置（`beimpl`、`bestream`、`bepartition`、`beepoch`、`beseq`），与收件表行同一事务写入（迁移 0014）。订阅的每个实例开始接收之前，在 `be_subscription_run` 记一行启动时刻（库的时钟，与收件表的处理时刻同一个钟） | SDK 测试 |
| P6.37 | 必须 | **进度**：一个订阅对（产生方，实现实例，流，分区）的进度，是收件表里处理时刻不晚于截止时刻 c 的、带位置的行的最大（纪元代次，纪元时间线，序号）；没有这样的行时为空。c 按运行段求：启动时刻把订阅的处理分成段，从最后一段起，这一段的启动时刻不晚于它最后一次处理的时刻减 L 时，c 就是那个时刻减 L；否则看上一段，依此类推；都不满足时 c 不存在，进度为空。L 是投递寿命的上限，起始 10 分钟，不短于确认等待乘投递上限加各次退避（P6.19、P6.20）；处理一条消息超过 L 的一半时记告警日志（`event_handling_slow`）。理由：同一分区的消息按位置顺序第一次投递，一条消息在运行中 L 之内必有结局（进收件表、进死信或不属于这个订阅）；所以位置不超过进度的都已有结局。只取“已处理的最大位置”不对：无序订阅里一条在退避重投的消息后面的照样处理；单副本停机时崩溃前投递的消息要等重启才重投，所以按运行段算 | 向量 `inbox-progress`、SDK 测试 |
| P6.38 | 必须 | **补发**：有流的组件在系统面提供 `be.source.v1.ResendService.Resend`（`proto/be/source/v1/resend.proto`），部署内任何服务身份可以调用。它把请求的流的每个分区里位置在起点之后的已发布行，按位置顺序（纪元在前）重新交给运输：事件身份与消息头不变，消息身份是 `<事件身份>/resend/<请求身份>`（只回退了消费者库时，原消息还在运输的去重窗口里）；请求没列出的分区、或起点的实现实例不是自己的，从保留的第一行起。回答补发的条数，以及两类分区：`beyond_retention`，起点之后的行有被清掉的（起点不晚于计数行记下的清理位置，或没有起点而清理过）；`ahead`，起点不在自己的纪元历史里，或越过了那个纪元的分叉点或当前计数（生产者回退过了消费者见过的行） | SDK 测试 |
| P6.39 | 必须 | **消费者的库回退之后**：消费者在 `be_consumer_epoch` 记下上次运行时库的纪元。启动时纪元与它不同（库回退过：恢复代次推进或时间线变了）时，对收件表里见过的每个（产生方，流），以各订阅里最小的进度为起点（按分区）经依赖地址调产生方的 `Resend`，都答完了才更新这一行；照常接收，不等补发（收件表去重）。没有那个产生方的地址时记错误日志 `event_resend_unreachable`，由恢复工具补做。第一次启动只记下纪元 | SDK 测试 |
| P6.40 | 必须 | `beyond_retention` 的分区：读模型（[09](09-lists-search-projections.md)）按快照修复；别的订阅在 `be_resend_gap` 记一行并记错误日志 `event_resend_beyond_retention`，恢复报告列出（装配项目协议 15 的 RC04）。`ahead` 的分区同样记一行，错误日志 `event_resend_consumer_ahead` | SDK 测试 |
