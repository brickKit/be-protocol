# 06 事件：信封、发件表与运输

依据：装配项目协议 02 的 S2（信封字段的唯一清单）、“来源一侧编号、纪元与补取”的第 2、3 步、“接收规则”与参数起始值；协议 14 的“库内计数与纪元”；协议 15 的“发件表的保留与消费者进度”；“事务与消息”“消息运输与事件信封”。本章写生产者一侧（发件表、锁内编号、纪元、转发）、运输端口与两个适配器、消费者的去重、死信与大消息。水位来源的回声、补取与消费者的连续位置、对齐随后续任务加入本章。

## 流、分区与发件表

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.1 | 必须 | 事件属于一个**流**（契约中声明的名字，小写字母、数字、下划线与点，例如 `erp.inventory.stock`），流声明分区数（1–256，发布后不改）。一条记录的事件只进一个分区：分区 = FNV-1a 64 位（记录身份的小写规范字符串的 UTF-8 字节）对分区数取余 | 向量 `partition` |
| P6.2 | 必须 | 业务写入与发件行在同一个本地事务中提交（经 [05](05-database.md) 的事务入口）；发件行不在事务外写，也不先发后写 | CK-EV-01 |
| P6.3 | 必须 | 发件表、分区计数行、纪元历史与部署恢复代次都在组件自己的 schema，由 SDK 的迁移建立（本仓库 `migrations/`）；表的形状对三种语言相同 | CK-DB-05 |
| P6.4 | 必须 | 每条发件行在写入时得到：事件身份（UUIDv7）、流、分区、插入顺序（库内序列）、事件类型、记录身份与版本、投影语义（`full`、`partial`、`delete`）、法人（交易事实）、受影响的主体（水位来源）、因果（上一个事件的身份）与跳数、追踪上下文、载荷，以及**行摘要** = SHA-256（事件身份的规范字符串、一个 0 字节、载荷字节）的小写十六进制；发布位置与纪元在编号时才写 | 向量 `envelope` |

## 锁内编号与纪元

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.5 | 必须 | **提交后编号**：每个（流，分区）一行计数。编号事务先锁计数行，取得锁之后用新的语句快照选出可见、尚未编号的发件行，按插入顺序编连续的发布位置（从计数加一起），与计数一起提交。事务内不做网络调用；锁等待 2 秒、整个事务 5 秒（PostgreSQL 17 起用 `transaction_timeout`，更早用 `statement_timeout` 加 `idle_in_transaction_session_timeout`），超时回滚 | CK-EV-02 |
| P6.6 | 必须 | 两个副本（或转发与补取）同时编号时，发布位置不重复、不跳号；回滚的行从不可见，不留空洞；长事务只推迟它自己的行 | CK-EV-02 |
| P6.7 | 必须 | **纪元** =（部署恢复代次，当前写入时间线），按这个顺序比较。部署恢复代次存在组件 schema 的单行表 `be_recovery_generation`（安装时 1，使库内容回退的操作在解冻前推进它）；时间线取当前 WAL 文件名的前 8 位十六进制。SDK 的迁移提供易变函数 `be_current_db_epoch()` 读取二者 | CK-EV-03 |
| P6.8 | 必须 | 编号事务读到的纪元与计数行记录的不同时，在纪元历史 `be_epoch_history` 中写下（流，分区，旧纪元，分叉点 = 旧纪元保留下来的最后位置，新纪元），新纪元的位置从 1 开始；读不到代次或时间线（例如在只读副本上）时拒绝编号 | CK-EV-03 |
| P6.9 | 必须 | 发布位置写作（实现实例，纪元，序号）。实现实例是安装时生成的随机身份，由配置键 `IMPLEMENTATION_INSTANCE` 提供（UUID，成员级；产生事件的组件必填），不存库、不随库恢复改变 | 向量 `envelope` |

## 转发

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.10 | 必须 | 转发按位置顺序发布已编号、未发布的行，等运输的持久确认之后才标记为已发布；确认丢失时再发一次（至少一次）。消息身份 = 事件身份，运输在去重窗口内据此去重 | CK-EV-04 |
| P6.11 | 应当 | 转发按（流，分区）取租约以减少争用；租约不承担正确性：停顿后恢复的旧持有者也只能排队取编号锁，重复发布由消费者去重 | — |
| P6.12 | 必须 | 已发布的行按补发保留（装配项目协议 15 的参数，起始 7 天）保留，与消费者是否确认无关；超过的由 SDK 自带的 singleton 作业 `be.outbox.purge`（每小时）删除，未发布的行从不删除；未发布的积压单独度量与告警 | CK-EV-05 |

## 信封

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.13 | 必须 | 信封用 CloudEvents 1.0 二进制模式：每个属性一个消息头，名字为 `ce-` 加属性名；载荷就是业务对象（JSON），`ce-datacontenttype` 为 `application/json`。属性与消息头见下表；消费者不认识的扩展属性原样保留、不报错 | 向量 `envelope` |
| P6.14 | 必须 | 消息头连同载荷有大小上限；载荷超过 64 KiB 时放进对象存储：生产者在转发时（事务外）把载荷写到自己的桶与前缀下的 `<前缀>events/<事件身份>`，事件的载荷换成引用对象 `{"claim":{"uri":…,"size":…,"sha256":…}}`，`ce-beclaim` 为 `true`。`uri` 是这个对象的预签名只读地址（GET），有效期等于运输保留（7 天，也是 S3 签名第 4 版的上限）；再次发布（补发）时重新签发。订阅者用普通的 HTTP GET 取回，不持有生产者的存储凭据，核对大小与摘要，不符按处理失败。对象的保留不短于运输保留、补发保留与最长对齐时长三者中最长的一个，由部署的生命周期规则负责（装配项目协议 12、15） | CK-EV-06 |
| P6.15 | 必须 | 处理一个事件时产生的新事件带 `becausation` = 该事件的身份、`behops` = 它的跳数加一；跳数超过 10 时按处理失败，不发出（成环的因果链在跳数上限处截断） | CK-EV-07 |

| 属性（消息头 `ce-<属性>`） | 必有 | 内容 |
| --- | --- | --- |
| `specversion` | 是 | `1.0` |
| `id` | 是 | 事件身份 |
| `source` | 是 | `urn:be:<产生方组件 ID>` |
| `type` | 是 | 事件类型（契约中声明，带主版本，例如 `erp.inventory.stock_moved.v1`） |
| `time` | 是 | 写发件行时的 UTC 时刻，RFC 3339，毫秒 |
| `subject` | 是 | 记录身份 |
| `datacontenttype` | 是 | `application/json` |
| `bestream`、`bepartition` | 是 | 流与分区 |
| `beimpl` | 是 | 实现实例 |
| `beepoch` | 是 | 纪元，写作 `<代次>.<时间线>`（十进制） |
| `beseq` | 是 | 分区内的发布位置（十进制） |
| `beversion` | 是 | 记录版本（十进制） |
| `beprojection` | 是 | `full`、`partial` 或 `delete` |
| `bedigest` | 是 | 行摘要（P6.4） |
| `behops` | 是 | 跳数，起点 0 |
| `becausation` | 否 | 上一个事件的身份 |
| `belegalentity` | 交易事实 | 法人 |
| `besubjects` | 水位来源 | 受影响的主体：JSON 字符串数组，最多 1,000 个 |
| `beclaim` | 否 | `true` 表示载荷是对象存储引用（P6.14） |
| `traceparent`、`tracestate` | 否 | W3C 追踪上下文（CloudEvents 分布式追踪扩展） |

## 运输端口

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.16 | 必须 | 运输由 `BUS_URL` 的 scheme 选择：`nats://` 为 NATS JetStream，`pgqueue://` 为 PostgreSQL 队列。同一条运输链的生产者与全部订阅者用同一个总线 | CK-BUS-01 |
| P6.17 | 必须 | 主题 = `be.<流>.<分区>.<事件类型>`。JetStream 中每个流一个 stream（名字 `BE_` 加流名，点换成下划线、大写），主题 `be.<流>.>`，文件存储；生产者启动时建立，已存在时不改它的设置 | CK-BUS-02 |
| P6.18 | 必须 | 订阅是持久的，名字 = 订阅方组件 ID 加订阅名（`/`、`.`、`-` 换成下划线）。同一订阅的多个实例竞争领取，每条消息由其中一个处理；不同订阅（包括同一外壳的两个成员）各收一份。建立订阅幂等，已存在时不改它的设置 | CK-BUS-03 |
| P6.19 | 必须 | 处理成功并且业务写入已提交之后才确认；处理失败时否认，按退避重投（起始 1 秒，每次加倍，上限 30 秒）；未确认的消息在确认等待（30 秒）后重投；处理中的消息可以续期，防止慢消息被重投 | CK-BUS-04 |
| P6.20 | 必须 | 投递次数达到上限（3）仍失败的消息进死信：订阅方在自己的库里记一条死信（同一订阅、同一事件身份只一条），然后终止这条消息的投递；死信由查询与人工处理接管，不依赖“下一次投递” | CK-BUS-05 |
| P6.21 | 必须 | 消息头在运输中往返不变；超过运输上限的消息发布时明确失败，不截断 | CK-BUS-06 |
| P6.22 | 必须 | 尽力而为的通知（缓存失效之类）不存储、不重投；订阅者离线时错过 | CK-BUS-07 |
| P6.23 | 必须 | PostgreSQL 队列：表在总线库自己的 schema（本仓库 `migrations-bus/`）。消息按（事务号，库内序号）排列，订阅的读取位置也是这一对；读取者只读事务号低于 `pg_snapshot_xmin` 的行（低于它的事务都已结束，之后也不会再出现更小的事务号）。只按序号加 xmin 屏障不够：事务号较小、序号较大的行先提交时，位置会越过一个仍在途、序号较小的行，那一行之后提交也不会被读到，而且不报错 | CK-BUS-08 |
| P6.24 | 内部 | 两个适配器跑同一组运输检查；对一个会丢确认的假适配器跑这组检查必须失败 | SDK 测试 |
| P6.27 | 必须 | 消息系统只是运输缓冲：消息按运输保留（起始 7 天，与补发保留相同）删除，与订阅是否读到无关。JetStream 的流建立时设 `MaxAge`（已存在的流按 P6.17 不改，在这条规则之前建立的流由运维设定）；PostgreSQL 队列由打开运输的每个进程每小时删除超过保留的消息与指向它们的投递（删除幂等）。离线超过保留的订阅者从流里丢失这段事件，靠发件表的补发与对齐恢复（装配项目协议 15、协议 02） | CK-BUS-09 |

## 消费者

| 编号 | 层级 | 规则 | 检验 |
| --- | --- | --- | --- |
| P6.25 | 必须 | 只订阅部分事件类型的消费者按收件表去重：（订阅，事件身份）唯一，与业务写入在同一个本地事务；重复投递只生效一次 | CK-EV-08 |
| P6.26 | 必须 | 收件表按去重寿命保留（最长重试、重放、死信重投与恢复窗口），不按短期的请求缓存清理；清理边界由覆盖它的版本或墓碑证明 | — |

## 检查编号

| 编号 | 检查 |
| --- | --- |
| CK-EV-01 | 业务事务回滚时没有发件行；提交后才有 |
| CK-EV-02 | 两个转发同时编号：位置连续、不重号；长事务的行晚于先提交的行编号，不留空洞 |
| CK-EV-03 | 推进部署恢复代次后，新纪元从 1 编号，纪元历史记下分叉点 |
| CK-EV-04 | 发布确认丢失后再发一次；消费者只生效一次 |
| CK-EV-05 | 已发布的行在补发保留内仍可读取 |
| CK-EV-06 | 64 KiB 以上的载荷经对象存储；摘要不符按处理失败 |
| CK-EV-07 | 跳数超过 10 的事件不发出 |
| CK-EV-08 | 同一事件投递两次，业务效果一次 |
| CK-BUS-01 … 08 | 运输检查，两个适配器各跑一遍（见 SDK 的一致性套件） |
| CK-BUS-09 | 超过运输保留的消息被删除，订阅没读到的也删；保留期内的不删 |
