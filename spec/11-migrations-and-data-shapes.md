# P11 Migrations and data shapes

How migrations run and what they may contain, the platform migration the runtime adds after the component's own, and the column shapes every component uses: keys, money, quantities, instants, business dates, the legal entity and document numbers.

## Requirements

| ID | Level | Requirement | Cases |
|---|---|---|---|
| P11.1 | MUST | Migrations log in as the owner `PG_OWNER_USER` (password from the file `PG_OWNER_PASSWORD_FILE`) and connect directly to PostgreSQL: to `PG_MIGRATION_HOST` / `PG_MIGRATION_PORT` when set, each falling back to `PG_HOST` / `PG_PORT` (the component's own keys, as brickKit recommends: the migration container has exactly the service's environment). Session parameters: `lock_timeout = 5s`, `statement_timeout = 15min`. A lock timeout is retried with backoff up to 3 times; the final failure logs the blocking backends' pids and wait events, and the first 200 characters of their SQL only where `pg_stat_activity` shows it (it hides another role's query text, and the owner is not granted `pg_read_all_stats`). The migration connection is a dedicated session: the migration tool's session-level `search_path` and session-level advisory lock are allowed on it (the exception to [P10.2](10-database.md) and [P10.8](10-database.md)). The migration lock is per schema: two components migrating the same database at the same time both succeed | CP-CORE-01 |
| P11.2 | MUST | Migration files contain no `OWNER TO`, `GRANT`, `REVOKE`, `CREATE SCHEMA`, `CREATE ROLE`, `ALTER ROLE`, `SET`, no schema-qualified names, no role or schema literal, and no partition bounded by a date literal. Names are unqualified and resolve through `search_path` | CP-DB-01 (gate `migration-identity-scan`) |
| P11.3 | MUST | The migration state tables live in the component's own schema; the official SDKs use the names in [the table below](#migration-state-tables), and they are exempt from P11.11. After the component's migrations, in the same migration step and as the owner, the runtime runs the **platform migration**, in this order: create or upgrade the `besdk_*` tables and the platform functions ([ddl/](../ddl/)), recording the version in `besdk_platform_version`; create the current partition window of every partitioned table from `lifecycle.yaml` ([P16.6](16-data-lifecycle.md)); ensure the event streams and the component's durables exist ([P12.4](12-events.md), [P12.5](12-events.md)). All three are idempotent. The `besdk_*` tables match the reference DDL column for column; the authorization projection ([ddl/07-authz-projection.sql](../ddl/07-authz-projection.sql)) is created only in the schema of a component that declares `resources` in `assembly.yaml` ([P6.12](06-authorization.md)) | CP-DB-04, CP-LIFE-01 |
| P11.4 | MUST | Schema evolution is expand / contract. A contract migration starts with the header line `-- be:contract after=<version>`, where `<version>` is the last version of the component that still uses what the step removes. Before such a file the migrator reads `pg_stat_activity` (whose `application_name` every role may see) and, while any other session named `<the same component ID>@<v>` with `v` ≤ `<version>` (semantic-version order) is connected ([P10.2](10-database.md), [P10.5](10-database.md)), stops before that file: the files before it stay applied, one ERROR line names the file, the blocking versions and their session count, and the migration step exits **1**; it is run again once the older processes are gone; a `CREATE INDEX CONCURRENTLY` is alone in its file, which starts with `-- be:no-transaction`. Production only migrates forward | — (gate) |
| P11.5 | MUST | Every own primary key is a UUIDv7 (RFC 9562), column type `uuid`, generated by the application before the insert, never by a column default. On a partitioned table the primary key is `(id, created_at)` and `created_at` equals the timestamp embedded in the id. A reference to another component's record is `TEXT`, with no foreign key. On the wire an id is an opaque string, the canonical 36-character lowercase form. Exceptions: a strictly monotonic counter is `BIGINT GENERATED ALWAYS AS IDENTITY`; a reference table keyed by a standard code (currency, unit) uses the code as `TEXT` | CP-DB-01 (gate `id-type-scan`) |
| P11.6 | MUST | Column shapes: amount `NUMERIC(19,4)`; unit price, cost and quantity `NUMERIC(19,6)`; exchange rate `NUMERIC(19,10)`; ratio (discount, tax rate) `NUMERIC(9,6)`; unit conversion factor `NUMERIC(24,12)`; currency `CHAR(3)` (ISO 4217 alphabetic, upper case). An amount is always paired with a currency on its document. Rounding happens only in the runtime's money implementation, to the currency's ISO 4217 minor units, `HALF_AWAY_FROM_ZERO` by default (`HALF_EVEN` on request); allocation uses the largest remainder. On the wire amounts, prices, quantities, exchange rates and ratios are decimal strings: optional `-`, digits, optional `.` and digits; no exponent, no `+`, no separators, no `NaN`; anything else is `INVALID_ARGUMENT` | — (vectors `money`) |
| P11.7 | MUST | An instant is `timestamptz`, sent as RFC 3339 UTC with `Z`. A business date is `DATE`, sent as `YYYY-MM-DD`, computed in the **legal entity's** business time zone. SQL never uses `CURRENT_DATE`, `now()::date`, `date_trunc(…, now())` or `::date` on a `timestamptz`: "today" and every date boundary are computed by the runtime and passed as parameters. A `DATE` is compared only with a `DATE`. Events carry their document's business dates. The runtime embeds its own IANA time-zone database (Go `time/tzdata`, the Python `tzdata` package, Node with full ICU) and never depends on the image's `/usr/share/zoneinfo`; it reports the version in `/_be/info` (`tzdata`), and the calendar vectors are re-run whenever that version changes | — (gate `business-date-scan`, vectors `calendar`) |
| P11.8 | MUST | Every transaction-document table has `legal_entity_id TEXT NOT NULL`, and every event about a transaction document carries `legal_entity_id` in its payload and `ce-legalentity` in its envelope. A consumer dead-letters such an event when the legal entity is missing; it never books it to a default | CP-EVS-07 |
| P11.9 | MUST | A legal entity's calendar (business time zone, fiscal-year start month, functional currency) comes from `mdm/org`, kept locally through a snapshot ([P15](15-snapshots.md)); exchange rates come from `mdm/currency`. There is no shared configuration variable for legal entities and no fixed rate. When `mdm/org` is not installed (no `MDM_ORG_ENDPOINT`, [P2.5](02-configuration.md)) the runtime's calendar runs in **degraded mode**: every legal entity uses `BUSINESS_TIMEZONE`, fiscal-year start month 1 and its id as its `{le}` code, and `/_be/info` lists `calendar` in `degraded` ([P20](20-self-description-and-versioning.md)). The mode is decided at start from the configuration, never per call | — |
| P11.10 | MUST | Document numbers come from the table `besdk_number_series` ([ddl/](../ddl/)), keyed `(series, scope, period)`. A **gap-free** series (`gapless = true`, accounting vouchers) locks its row in the same transaction as the document, so numbers are continuous within the period and a rollback returns the number; numbers are allocated only after the idempotency claim succeeded. Other series reserve blocks in a short transaction of their own and may have gaps, never repeats. The format is the component's configuration key `<SERIES>_NO_FORMAT` with placeholders `{le}`, `{yyyy}`, `{yy}`, `{mm}`, `{seq:N}`; dates in the format are business dates. Uniqueness is enforced by the unpartitioned platform table `besdk_number_allocations`, primary key `(legal_entity_id, series, number)` ([ddl/](../ddl/)): the runtime inserts every formatted number there in the document's own transaction, so a repeat fails that transaction with SQLSTATE `23505` on that table (a series misconfiguration, surfaced as `INTERNAL`) and a rollback frees the number. A unique constraint on the document table itself is not the mechanism: a unique index on a partitioned table must contain the partition key, so `(legal_entity_id, number)` cannot be unique across partitions | — (vectors `numbering`) |
| P11.11 | MUST | Every table a component's migrations create is declared in `migrations/lifecycle.yaml` ([P16.1](16-data-lifecycle.md)). The `besdk_*` tables and the official migration-state tables are exempt; a component whose runtime is not an official SDK declares its migration tool's state tables as `class: platform`. The migrations directory holds only `*.sql` files and `lifecycle.yaml` | CP-LIFE-04 |

## Column shapes

| What | Column | Wire |
|---|---|---|
| own id | `uuid` (UUIDv7) | string, 36 chars, lowercase |
| reference to another component's id | `TEXT` | opaque string |
| instant | `timestamptz` | RFC 3339 UTC, `Z` |
| business date | `DATE` | `YYYY-MM-DD` |
| amount | `NUMERIC(19,4)` + `currency CHAR(3)` | decimal string at the currency's minor units, plus `currency` |
| functional-currency amount | `NUMERIC(19,4)` | decimal string |
| unit price, cost, quantity | `NUMERIC(19,6)` | decimal string, up to 6 decimals |
| exchange rate | `NUMERIC(19,10)` with `fx_rate_date DATE`, `fx_rate_type TEXT` | decimal string, up to 10 decimals |
| ratio | `NUMERIC(9,6)` | decimal string, `0.130000` = 13 % |
| conversion factor | `NUMERIC(24,12)` | decimal string |
| legal entity | `legal_entity_id TEXT NOT NULL` | string |

## Migration file headers

| Header (first line) | Meaning |
|---|---|
| `-- be:no-transaction` | the file runs outside a transaction (only `CREATE INDEX CONCURRENTLY`, alone) |
| `-- be:contract after=<version>` | a contract step; `<version>` is the last version that still uses what it removes; run only once no session of that version or an older one is connected (P11.4) |

## Migration state tables

| Runtime | Component migrations | Platform migration | Migration lock (per schema, waits) | `lifecycle.yaml` skipped by |
|---|---|---|---|---|
| be-sdk-go (golang-migrate) | `schema_migrations_<PG_SCHEMA>` | `besdk_migrations_<PG_SCHEMA>` | the tool's session advisory lock, its id derived from database, schema and state table | the source reads only `<version>_<name>.up.sql` / `.down.sql` |
| be-sdk-python (yoyo) | `_yoyo_migration`, `_yoyo_log`, `_yoyo_version`, `yoyo_lock` | the same tables; platform migration ids start with `besdk-` | the row in `yoyo_lock` of the schema | the tool reads only `*.sql` and `*.py` |
| be-sdk-ts (node-pg-migrate) | `pgmigrations_<PG_SCHEMA>` | `besdk_migrations_<PG_SCHEMA>` | the tool's advisory lock with `lockValue` derived from `PG_SCHEMA` (its constant default would make every schema share one lock); the runtime retries until it holds it, because the tool alone fails at once | `ignorePattern` that excludes everything but `*.sql` |

A runtime in another language declares its own tool's tables as `class: platform` (P11.11) and states its lock in its `AGENTS.md`; the lock MUST be per schema (P11.1).

## Notes

- The platform migration's DDL is normative: the suite compares the catalogue of a migrated schema with [ddl/](../ddl/) (`CP-DB-04`).
- A column's scale is its capacity, not its precision: the stored value has already been rounded to what the currency or unit allows.
